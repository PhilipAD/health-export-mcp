Apple Health export.xml to JSON — The Complete Guide (2026)

Every Apple Health user eventually hits the export.xml wall. You request your data from Settings → Health → Export All Health Data, wait a few minutes, and Apple hands you a single XML file. If you've been collecting data for a year, that file is 200 MB. Five years? 800 MB to 1.5 GB. Ten years of sleep, heart rate, and workout data can push past 2 GB.

The wall is this: almost nothing modern works with XML. AI agents, data pipelines, and analysis tools all speak JSON. An MCP server needs JSON to serve health data to Claude or Cursor. A Python data-science script loads from JSON. A custom GPT's Actions endpoint sends and receives JSON. Export.xml is a dead end unless you convert it first.

This guide covers every real method for going from export.xml to usable JSON in 2026 — including one method that skips the XML entirely.

What export.xml looks like — and why it's painful

Apple's export.xml uses a flat record structure. Every health data point — every heart rate reading, every step count, every sleep stage — is a single <Record> element:

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE HealthData [
  <!ELEMENT HealthData (ExportDate,Me,(Record|Correlation|Workout)*)>
  <!ATTLIST HealthData locale CDATA #REQUIRED>
]>
<HealthData locale="en_US">
  <ExportDate value="2026-07-25 12:00:00 +0000"/>
  <Me>
    <HKCharacteristicTypeIdentifierDateOfBirth value="1990-01-15"/>
    <HKCharacteristicTypeIdentifierBiologicalSex value="HKBiologicalSexMale"/>
    <HKCharacteristicTypeIdentifierBloodType value="HKBloodTypeAPositive"/>
  </Me>
  <Record type="HKQuantityTypeIdentifierHeartRateVariabilitySDNN"
          sourceName="Apple Watch"
          sourceVersion="10.3"
          unit="ms"
          creationDate="2026-07-25 08:30:00 +0000"
          startDate="2026-07-25 08:30:00 +0000"
          endDate="2026-07-25 08:31:00 +0000"
          value="42.5"/>
  <!-- 200,000+ more records... -->
</HealthData>

Three problems make this file painful in practice:

  1. Size. DOM parsers load the entire tree into memory. A 1 GB export.xml needs 3-5 GB of RAM to parse with xml.dom.minidom. Even SAX/streaming parsers take measurable time — 45-90 seconds for a 500 MB file on modern hardware.
  2. Nesting. Records inside Correlations inside Workouts. You can't just grep for <Record and get clean data — value is an attribute, some records store metadata children, and the type attribute uses Apple's internal HKTypeIdentifier strings that need human-readable aliases.
  3. No structure. Everything is a flat Record element with type/date/value. There's no schema for time series — data comes as individual atoms (one heart rate reading per element), and you have to group them into daily, weekly, or monthly aggregates yourself.

Method 1 — Python streaming parser (fast, one-time)

Python's xml.sax module handles large XML files without loading them into memory. This parser reads export.xml record-by-record, converts each to a JSON object, and writes to a NDJSON file (one JSON object per line):

#!/usr/bin/env python3
"""Stream Apple Health export.xml to NDJSON — handles any file size."""
import json, xml.sax, xml.sax.handler, sys
from pathlib import Path

class HealthHandler(xml.sax.handler.ContentHandler):
    def __init__(self, out):
        self.out = out
        self._current = None
    def startElement(self, name, attrs):
        if name == "Record":
            record = {
                "type": attrs.get("type", ""),
                "sourceName": attrs.get("sourceName", ""),
                "sourceVersion": attrs.get("sourceVersion", ""),
                "unit": attrs.get("unit", ""),
                "value": attrs.get("value", ""),
                "startDate": attrs.get("startDate", ""),
                "endDate": attrs.get("endDate", ""),
                "creationDate": attrs.get("creationDate", ""),
            }
            self.out.write(json.dumps(record) + "\n")
        elif name == "Workout":
            w = {
                "_type": "Workout",
                "workoutType": attrs.get("workoutActivityType", ""),
                "duration": attrs.get("duration", ""),
                "durationUnit": attrs.get("durationUnit", ""),
                "startDate": attrs.get("startDate", ""),
                "endDate": attrs.get("endDate", ""),
                "energyBurned": attrs.get("totalEnergyBurned", ""),
            }
            self.out.write(json.dumps(w) + "\n")

with open("export.xml") as f:
    out = open("apple-health.ndjson", "w")
    xml.sax.parse(f, HealthHandler(out))
    out.close()

print("Done — wrote apple-health.ndjson")

This produces a line-delimited JSON file. Each line is one record. To convert to a single structured JSON document (grouped by metric type, with daily aggregations), pipe through a second pass:

cat apple-health.ndjson | python3 -c "
import json, sys
from collections import defaultdict

daily = defaultdict(lambda: defaultdict(list))

for line in sys.stdin:
    r = json.loads(line)
    if '_type' in r:
        continue  # skip workout summaries
    mtype = r['type'].replace('HKQuantityTypeIdentifier', '')
    date = r['startDate'][:10]  # YYYY-MM-DD
    try:
        daily[mtype][date].append(float(r['value']))
    except ValueError:
        pass

output = {}
for mtype, dates in daily.items():
    output[mtype] = {
        'unit': 'unit_placeholder',
        'daily': [
            {'d': d, 'v': round(sum(vals)/len(vals), 2)}
            for d, vals in sorted(dates.items())
        ]
    }

json.dump(output, sys.stdout, indent=2)

Method 2 — Node.js streaming parser (for ESM-native pipelines)

If your data pipeline is already in JavaScript/TypeScript, Node's saxes package (a SAX-style streaming XML parser) works well. Install with npm install saxes:

import { promises as fs } from 'node:fs';
import { createReadStream, createWriteStream } from 'node:fs';
import saxes from 'saxes';
import { Transform, pipeline } from 'node:stream';

const types = {
  HKQuantityTypeIdentifierHeartRateVariabilitySDNN: 'HRV SDNN',
  HKQuantityTypeIdentifierRestingHeartRate: 'RestingHeartRate',
  HKQuantityTypeIdentifierStepCount: 'Steps',
  HKQuantityTypeIdentifierAppleSleepingWristTemperature: 'SleepWristTemp',
};

const parser = new saxes.SaxesParser({});
const output = createWriteStream('health.jsonl');

parser.on('opentag', (node) => {
  if (node.name === 'Record') {
    const a = node.attributes;
    const record = {
      type: types[a.type] || a.type?.replace('HKQuantityTypeIdentifier', ''),
      value: parseFloat(a.value) || a.value,
      unit: a.unit,
      date: a.startDate,
      source: a.sourceName,
    };
    output.write(JSON.stringify(record) + '\n');
  }
});

createReadStream('export.xml')
  .pipe(new Transform({
    transform(chunk, enc, cb) { parser.write(chunk.toString()); cb(); }
  }))
  .on('finish', () => { parser.close(); output.end(); });

The Node.js approach is slightly slower than Python's native SAX (about 20-30% higher parse time on the same file) but integrates naturally if you're running an Express server or an MCP server that already processes health data.

Pain points you'll hit with export.xml (and how to work around them)

1. The HKTypeIdentifier aliases

Apple uses verbose internal identifiers like HKQuantityTypeIdentifierHeartRateVariabilitySDNN. Every converter needs a lookup table. Here's a starter set of the most common:

HKQuantityTypeIdentifierHeartRateVariabilitySDNN → HRV SDNN
HKQuantityTypeIdentifierRestingHeartRate         → RestingHeartRate
HKQuantityTypeIdentifierStepCount                 → Steps
HKQuantityTypeIdentifierAppleSleepingWristTemperature → SleepWristTemp
HKQuantityTypeIdentifierActiveEnergyBurned        → ActiveEnergy
HKQuantityTypeIdentifierBasalEnergyBurned         → BasalEnergy
HKQuantityTypeIdentifierDietaryEnergyConsumed     → DietaryEnergy
HKQuantityTypeIdentifierFlightsClimbed            → FlightsClimbed
HKQuantityTypeIdentifierWalkingHeartRateAverage   → WalkingHeartRate
HKQuantityTypeIdentifierEnvironmentalAudioExposure → AudioExposure

The XML lists type as a string attribute. A replace('HKQuantityTypeIdentifier', '') in your converter handles most of them, but you'll still want a manual alias map for a few hundred metrics.

2. The Me element

Your biological sex, date of birth, blood type, and skin type are embedded in the <Me> element at the top of the file. These are characteristic-type identifiers, not records. Pull them separately and add them as metadata in your JSON output. The Health Export AI app includes these in the top level of its JSON output.

3. Correlations and Workout metadata

Some health metrics appear inside <Correlation> elements (e.g., blood pressure has systolic and diastolic sub-records). Both Python SAX and Node saxes emit these as independent <Record> elements because the parser doesn't track parent context in the handler callbacks. If you need correlation grouping, you'll need a stack-based state machine that tracks <Correlation> open/close. This is one area where the direct HealthKit approach genuinely wins — the iOS app resolves correlations in-memory before writing JSON.

Frequently Asked Questions

Why is my Apple Health export.xml so large?

Apple stores every individual health data point as a separate XML element. One heart rate reading = one Record element. If your Apple Watch samples heart rate every 5 minutes, that's 288 records per day, plus sleep stages (sampled per minute), plus steps, workouts, and any metrics from third-party apps. A year of moderate data collection produces 200-400 MB of raw XML. You can verify this by counting the <Record> elements in your export with grep -c '<Record' export.xml.

Can I load export.xml directly into an MCP server?

No — MCP servers communicate in JSON over stdio or WebSocket. The health-export-mcp server expects a .health-cache.json file, which is pre-structured JSON grouped by metric and day. You can convert export.xml to the same format using the two-pass method in this guide, but it's a one-time batch operation — the MCP server won't pick up new data until you re-convert and re-export.

How do I convert export.xml to CSV instead of JSON?

Use the same SAX streaming method but write CSV rows instead of JSON lines. Collect Record attributes into a list of dicts, then use Python's csv.DictWriter. The column schema is: type, value, unit, startDate, endDate, creationDate, sourceName, sourceVersion. Note that CSV doesn't handle nested or variable-width data well — correlation records and workout metadata are best kept in a separate file.

Does Health Export AI process my existing export.xml?

No — the iOS app reads data directly from HealthKit on your iPhone, the same database that Apple's own export.xml generator uses. There's no need to process an old export file when the app can access live data. The app's cache file is also 50-100x smaller than the equivalent export.xml because it aggregates to daily averages rather than storing individual samples.

What about privacy — does Health Export AI upload my data?

The iOS app is a local export tool. Data stays on your device unless you configure a webhook destination, and even then it POSTs directly to the endpoint you specify. The open-source MCP server runs entirely on your machine. No data passes through any developer-owned server.
