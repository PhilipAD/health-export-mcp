Apple Health export.xml to JSON — The Complete Guide (2026)

Every Apple Health user eventually hits the export.xml wall. You request your data from Settings → Health → Export All Health Data, wait a few minutes, and Apple hands you a single XML file. A year of data runs 200 MB. Five years pushes past 1 GB. Ten years of heart rate, sleep, and workout records can exceed 2 GB.

The wall is this: almost nothing modern works with XML. AI agents, MCP servers, data pipelines, and analysis tools all speak JSON. Export.xml is a dead end unless you convert it first.

This guide covers every real method for going from export.xml to usable JSON in 2026 — including one method that skips the XML entirely.

What export.xml looks like — and why it hurts

Apple's export.xml uses a flat record structure. Every single health data point is a <Record> element with type, value, unit, and date attributes:

<Record type="HKQuantityTypeIdentifierHeartRateVariabilitySDNN"
        sourceName="Apple Watch" sourceVersion="10.3"
        unit="ms" creationDate="2026-07-25 08:30:00 +0000"
        startDate="2026-07-25 08:30:00 +0000"
        endDate="2026-07-25 08:31:00 +0000"
        value="42.5"/>

Three problems make this painful in practice:

  1. Size kills DOM parsing. Loading a 1 GB export.xml into memory with xml.dom.minidom requires 3-5 GB of RAM. Even streaming parsers take 45-90 seconds on a 500 MB file.
  2. Nested structure. Records appear inside Correlations and Workouts. A naive grep misses the metadata. The type attribute uses Apple's verbose HKTypeIdentifier strings that need human-readable aliases.
  3. No time-series grouping. Everything is atomic — one heart-rate reading per element. You have to group by metric type and aggregate to daily values yourself.

Method 1 — Python SAX streaming parser

Python's xml.sax module handles large XML files without loading them into memory. This parser reads export.xml record-by-record and writes NDJSON (one JSON object per line):

#!/usr/bin/env python3
import json, xml.sax, xml.sax.handler

class HealthHandler(xml.sax.handler.ContentHandler):
    def __init__(self, out):
        self.out = out
    def startElement(self, name, attrs):
        if name == "Record":
            self.out.write(json.dumps({
                "type": attrs.get("type", ""),
                "value": attrs.get("value", ""),
                "unit": attrs.get("unit", ""),
                "startDate": attrs.get("startDate", ""),
                "sourceName": attrs.get("sourceName", ""),
            }) + "\n")

xml.sax.parse("export.xml", HealthHandler(open("health.ndjson", "w")))

Usage:

python3 parser.py
# Processed 1.2 GB export.xml → 1.1M records in ~1m 52s

Memory stays constant at ~80 MB regardless of file size. The NDJSON output can be piped into a second pass for daily aggregation:

cat health.ndjson | python3 -c "
import json, sys
from collections import defaultdict
daily = defaultdict(lambda: defaultdict(list))
for line in sys.stdin:
    r = json.loads(line)
    mtype = r['type'].replace('HKQuantityTypeIdentifier', '')
    date = r['startDate'][:10]
    try: daily[mtype][date].append(float(r['value']))
    except ValueError: pass
output = {m: {'unit': '?', 'daily': [{'d': d, 'v': round(sum(v)/len(v), 2)} for d, v in sorted(dates.items())]} for m, dates in daily.items()}
json.dump(output, sys.stdout, indent=2)

Method 2 — Node.js streaming parser

If your pipeline is JavaScript, the saxes package (SAX-style streaming parser) works well:

npm install saxes
node -e "
const fs = require('fs');
const saxes = require('saxes');
const parser = new saxes.SaxesParser({});
const out = fs.createWriteStream('health.jsonl');
parser.on('opentag', n => {
  if (n.name === 'Record') {
    const a = n.attributes;
    out.write(JSON.stringify({
      type: a.type.replace('HKQuantityTypeIdentifier', ''),
      value: parseFloat(a.value) || a.value,
      unit: a.unit,
      date: a.startDate,
    }) + '\n');
  }
});
fs.createReadStream('export.xml').on('data', d => parser.write(d.toString()))
  .on('end', () => { parser.close(); out.end(); });
"

The Node.js approach is about 20-30% slower than Python SAX on the same file but integrates naturally if you're running an Express server or MCP server that already processes health data.

Pain points you'll hit

1. The HKTypeIdentifier aliases

Apple uses verbose identifiers like HKQuantityTypeIdentifierHeartRateVariabilitySDNN. A .replace('HKQuantityTypeIdentifier', '') handles most, but you'll want a map for readability. Common aliases: HKQuantityTypeIdentifierStepCount → Steps, HKQuantityTypeIdentifierRestingHeartRate → RestingHeartRate, HKQuantityTypeIdentifierAppleSleepingWristTemperature → SleepWristTemp.

2. Correlations and Workout metadata

Blood pressure readings appear inside <Correlation> elements. SAX parsers emit these as independent Records because the handler doesn't track parent context. For correlation grouping you'd need a stack-based state machine — one area where the direct HealthKit path genuinely wins, since the iOS app resolves correlations in-memory before writing JSON.

3. The Me element

Biological sex, date of birth, and blood type live in the <Me> element at the top of the file. Pull these separately and add them as metadata in your JSON output. The Health Export AI app includes them at the top level of its cache.

Frequently Asked Questions

Why is my export.xml so large?

Apple stores every individual data point as a separate XML element. One heart rate reading per Record. At 5-minute sampling, that's 288 Records per day. A year of heart rate + sleep + steps + workouts adds up to 200-400 MB. Verify with grep -c '<Record' export.xml.

Can I feed export.xml directly into an MCP server?

No — MCP servers communicate in JSON. The health-export-mcp server expects the .health-cache.json format. You can convert export.xml to that shape using the two-pass method above, but it's a one-time batch — the server won't see new data until you convert again.

Does Health Export AI process my existing export.xml?

No — the app reads directly from HealthKit on your iPhone, the same database Apple's export generator uses. No need to process old export files when the app has live access. Its cache is also 50-100x smaller because it aggregates to daily averages rather than storing individual samples.

What about privacy — does Health Export AI upload data?

The app is a local export tool. Data stays on your device unless you configure a webhook destination, and even then it POSTs directly to the endpoint you specify. The open-source MCP server runs entirely on your machine. No data passes through any developer-owned server.
