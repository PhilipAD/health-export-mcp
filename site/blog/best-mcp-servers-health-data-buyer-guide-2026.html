Best MCP Servers for Health Data — A Buyer's Guide (2026)

The Model Context Protocol (MCP) has unlocked a new capability: your AI agent can read your real Apple Health data — HRV, sleep stages, steps, resting heart rate, VO₂ max — and answer questions from your actual numbers instead of a static CSV.

But which MCP server should you use? As of July 2026 there are five active projects, each with a different approach, different data sources, and different tradeoffs. This guide compares them all so you can pick the right one for your stack.

TL;DR — the one-sentence summary

If you use Apple Health, health-export-mcp is the only server that reads HealthKit directly without requiring you to manually export XML or learn SQL. If you use Garmin/Oura/Whoop, use ghurt.org. If you already have an export.xml and prefer DuckDB, @mseep/apple-health-mcp works but adds a query-language dependency.

1. health-export-mcp — the direct HealthKit bridge

health-export-mcp is the open-source MCP server paired with the Health Export AI iOS app. The app reads your HealthKit store directly — 190 metric types — and writes a structured .health-cache.json file to iCloud Drive. The MCP server reads that cache and exposes seven query tools to any MCP client.

What makes it different

No manual export step. Every other Apple Health MCP server requires you to go to Settings → Health → Export All Health Data, wait for the XML to generate, then point the server at that file. health-export-mcp's companion iOS app syncs automatically every 30 minutes — your agent always sees recent data.

Zero dependencies. The server is a single server.mjs file. No npm install of DuckDB, no Python runtime, no SQL parser. Run node server.mjs and it's ready.

Natural-language queries. The seven tools cover the most common agent patterns — query by metric and date range, get daily aggregates, list available metrics, compare date ranges, and more. Your agent can ask "What's my HRV trend this week?" without writing SQL.

Setup with Claude Desktop:

{
  "mcpServers": {
    "health-export": {
      "command": "node",
      "args": ["/path/to/health-export-mcp/server.mjs"],
      "env": {
        "HEALTH_DATA_DIR": "~/Library/Mobile Documents/iCloud~ai~healthexport~app/Documents"
      }
    }
  }
}

Or drag the health-export.mcpb file into Claude Desktop → Settings → Extensions.

Same config works for Cursor (~/.cursor/mcp.json), VS Code, opencode, and Hermes.

2. DuckDB-based servers (@mseep, @neiltron)

The @mseep/apple-health-mcp and @neiltron/apple-health-mcp packages take the same approach: they ingest export.xml into a DuckDB database, then expose a single SQL-execution tool. Your agent sends SQL queries and gets results back.

This is a technically sound architecture — DuckDB is fast, columnar, and excellent for time-series analytics. If you're already comfortable writing SQL, these servers give you complete flexibility. You can do arbitrary aggregations, window functions, and joins that the health-export-mcp tools don't expose directly.

However, the SQL requirement is a meaningful friction point. Most MCP clients don't know your database schema — your agent has to first discover which tables exist and which columns are available, then generate syntactically correct DuckDB SQL. In practice, this takes 2-3 extra round-trips per query. The developer experience is "ask the agent to query your health data, watch it guess the table name wrong, correct it, then get results."

Setup is also heavier:

# @mseep requires npm install (pulls in DuckDB native bindings)
npm install @mseep/apple-health-mcp
# Then convert export.xml to DuckDB:
npx apple-health-mcp ingest ~/Downloads/export.xml
# Then configure MCP pointing at the .duckdb file
ProCon
✓Arbitrary SQL — complete flexibilityRequires DuckDB native binary (~20 MB)

✓Can join across all health metrics in one query

3. apple-health-mcp-unofficial — local-first XML parser

The apple-health-mcp-unofficial package (v0.5.0) takes a different approach: it parses export.xml locally using a SAX-style streaming parser and exposes a set of query tools — similar in philosophy to health-export-mcp but reading from the raw XML export instead of a pre-structured cache.

Strengths: no DuckDB dependency, no SQL knowledge needed, local-first privacy model. The tool interface is straightforward — ask for metrics by name and date range, get JSON back.

Weaknesses: still requires an export.xml generation step, which means you go to Settings → Health → Export All Health Data every time you want fresh data. The SAX parser has to re-parse the full XML on every server start (45-90 seconds for a 500 MB file). And because it parses the flat XML record structure, correlation data (like blood pressure with systolic/diastolic pairs) gets flattened.

4. The original apple-health-mcp (abandoned)

The original apple-health-mcp (v0.1.0) read CSVs from the now-defunct Health Auto Export app (healthautoexport.com domain is dead). The server has no commits since mid-2025. If you find an old reference to it, don't build on it — there's no support, no updates, and the data source it depends on no longer exists.

5. ghurt.org — for Garmin, Oura, and Whoop (not Apple Health)

ghurt.org is the strongest MCP brand in the health-data space. It integrates with Garmin Connect, Oura Ring, and Whoop — but not Apple Health. If you wear an Apple Watch, ghurt can't read your data.

ghurt's approach is cloud-based: you authenticate with your wearable provider's API, and ghurt proxies that data to your MCP client. This gives it access to real-time data without manual exports, but it means your data passes through ghurt's server.

If you use Apple Health exclusively, ghurt is not an option. If you use a mix of Apple Watch and Oura/Garmin/Whoop, you'd need both health-export-mcp (for Apple Health) and ghurt (for the others).

How to choose

  • I have an Apple Watch and want to ask my agent about my health data without jumping through hoops. Use health-export-mcp with the free iOS companion app. No XML, no SQL, no DuckDB. Setup time: under 2 minutes.
  • I prefer SQL and want to do custom analytics across my full export history. Use @mseep/apple-health-mcp. Be prepared to help your agent discover the schema on first use.
  • I already have an export.xml and don't want to install anything new. Use apple-health-mcp-unofficial. It's lightweight and needs only Node.js.
  • I use Garmin/Oura/Whoop, not Apple Watch. Use ghurt.org.
  • I found the original apple-health-mcp package on npm. Don't use it — it's abandoned and its data source is defunct.

The practical difference shows up in data freshness. With health-export-mcp, the companion app syncs every 30 minutes, so last week's data is already cached and ready. With any XML-based server, you need to re-export from Settings → Health (which takes 5-15 minutes) and re-ingest (another 45-90 seconds of parsing) before your agent can see any new data points added to HealthKit by other apps.

The elephant in the room: privacy

All the servers compared here are local-first — they process your health data on your own machine. The MCP protocol runs over stdio (or localhost WebSocket for some clients). No server in this comparison uploads your raw health data to a cloud service by default.

The distinction is subtle but important: ghurt.org requires sending API tokens to their server (to proxy Garmin/Oura/Whoop). DuckDB-based servers download native DuckDB binaries from npm. health-export-mcp runs entirely on your machine with the companion app writing locally to iCloud Drive — no developer-owned server handles your data at any point.
